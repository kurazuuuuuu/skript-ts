## コマンド

`command(name, args, body, options?)` — 型付き引数を任意個まで定義できます
（意味論の全体は下記「コマンド定義」を参照）。`args` は従来形式の引数型1つ
（`"text"` / `"player"` / `"integer"`、常に省略可能、第4引数に真偽値も可）か、
`cmdArg(type, optional?)` のリストです。省略可能引数は `[<type>]`、
必須引数は `<type>` と出力されます。本体は `trigger:` セクションになります。

算術の意味論（本家 Skript 2.17.1 の実挙動で裏取り済み）: 被演算子は
原則として両方とも数値です。例外は `+` で、両方が文字列なら連結に
なります（`"5" + "6"` は数値の 11 ではなく文字列 `"56"`）。それ以外の
型の組み合わせ（文字列と数値の混在も、どちらの順でも）はエラーに
ならず「値なし」になります。**値なしの被演算子は型違いとは別物**
です（フェーズ13のプローブで確定）。4つの中置演算子では、相手が
数値なら値なしは 0 として扱われます（未設定の変数 `+ 100` は `100`、
`* 2` は `0`、`5 /` 未設定 は Infinity）。相手が文字列・真偽値の
場合と、両辺とも値なしの場合は「値なし」になります。除算は実数
除算で、ゼロ除算は doubles の規則に従います（`1 / 0` は Infinity）。
出力は常に括弧で囲むため、Skript 自身の演算子優先順位に依存し
ません。剰余は Skript の `mod()` 関数です（Skript に中置の剰余
演算子はありません）。数学的剰余で、結果の符号は除数に一致します
（`mod(-1, 10)` は `9`）。除数がゼロのときは NaN です。なお
`mod()` は 0 代入をしません（被演算子が値なしなら結果も値なし）。

乱数の意味論（本家 Skript 2.17.1 の実挙動で裏取り済み）: 抽選式は
評価のたびに新しい乱数を引く。シードはなく、どちらの実行系でも
再現性はない。両端とも数値でなければならない。値なし・数値以外の
端は「値なし」になる（本家で文字列の端が読み込みエラーになるのは
リテラルの場合のみで、変数に入った文字列は実行時に値なしになり、
エンジンと同じ挙動）。逆転した範囲は抽選前に
入れ替える。`randomNumber` は範囲内一様（両端が等しければその値
そのもの）。`randomInteger` は閉区間の中にある整数全体から一様に
引く（下端は切り上げ、上端は切り捨てで内側へ寄せる）。したがって
`randomInteger(1.5, 3.5)` は {2, 3} から、`randomInteger(-3.5, -1.5)`
は {-3, -2} から、`randomInteger(1, 3)` は {1, 2, 3} から引く。
整数を1つも含まない範囲（`randomInteger(1.2, 1.8)`）はエラーでは
なく「値なし」になる。

注意: `on death` イベントには `player` が存在せず、Skript にエラーとして
弾かれます（"There's no player in an on death event"）。死亡したプレイヤーは
`victim()` で表します。これは Skript 2.17.1 での実サーバー検証で見つかった
もので、まさにその検証段の存在理由です。

注意: 文字列の中で変数の値を展開するには `%...%` で囲む必要があります。
文字列内の素の `{...}` は Skript ではリテラル文字列として扱われます
（エラーにはならず、誤ったテキストがそのまま送信されます）。この囲みは
エミッタが行います。この問題は読み込み確認ではなく、後述の振る舞い
テストで検出されました。

比較の意味論（推測ではなく本家 Skript 2.17.1 の実挙動で裏取り済み）:
文字列の等値は **大文字小文字を区別しません**。異なる型の値は決して
等しくなりません（数値の `1` と文字列 `"1"` は非等値）。**値なし**
（未設定の変数）は何とも等しくなく、値なし同士でも等しくありません。
不等値は等値の厳密な否定で、未設定の変数は「0 ではない」が真に
なります。大小比較は数値のみに有効で、文字列や型の混在は偽に
なり、否定形も厳密な否定です（比較不能な組は「より大きくない」が
真）。エンジン jar も同じ意味論をネイティブに実装しています。

論理演算は `.sk` のテキストとしては出力しません。Skript 2.17.1 は
条件位置の接続表現を、試した全ての形（裸・括弧つき・他の条件との
混在）でパース拒否し、一般の `not` 条件も存在しないからです。
そのため `ifElse` は論理を制御フローへ展開します。`and` は2番目の
検査を1番目の中に入れ子にし（else 節を複製）、`or` は else 節側へ
入れ子にし、`not` は else がある場合は分岐交換、ド・モルガンの
適用、そして Skript ネイティブの否定形（`is not ...`、
`does not have permission`）を使い分けます。このサブセットの条件は
純粋（副作用なし）なので、この展開は意味論的に厳密です。エンジン
側は `and`/`or`/`not` を直接評価します。

chance の意味論（本家 Skript 2.17.1 の実挙動で裏取り済み）: 引数は
**割合**で、`chance(0.5)` は半分の確率で成功する。これは本家自身の
パーセントモデルで、`50%` リテラルは数値 0.5 であり、式の後ろに
パーセント記号を書く形（`chance of {p}%`）は 100 で割る。1 以上は
常に成功し、負の値は決して成功せず、値なし・数値以外も成功しない。
検査のたびに引き直すため、`whileLoop` の頭にも使える（反復ごとに
再抽選）。非対称な点が1つある。本家には **chance の否定形が存在
しない**ため、`not(chance(...))` は `if` に else 節がある場合のみ
展開でき（分岐交換）、なければ明示的なエラーでビルドが失敗する。
`whileLoop` の頭としての否定 chance は最初から拒否される。（本家
自身は空の `if chance ...:` 節を読み込み警告だけで受け入れ、それで
否定を表現することもできるが、skript-ts は警告を出す出力を避けて
明示的なビルドエラーを選んでいる。）

## リスト・ループ・while・wait

リストの意味論（推測ではなく、本家 Skript 2.17.1 へのプローブで
裏取り済み）。リストは独立した値ではなく、通常の変数ストアにある
`{name::<index>}` エントリの集合です。そのため永続化もスカラーと
同じ経路に乗り、エンジンでは `variables.json` に `name::index`
キーとして個別に保存されます。

- **添字の同定**: 式で計算された添字では、数値 `5` と文字列 `"5"` は
  **同じエントリ**です（同定は文字列表現によります）。変数名と
  文字列添字は大文字小文字を区別しません（小文字化して格納）。
- **走査順**: 文字列添字が先（数値らしい文字列は値の順、それ以外は
  アルファベット順）、その後に数値添字の昇順です。`loopList` は
  `loopValue()` と `loopIndex()` の両方を設定し、添字をテキストとして
  描くときは素の形（`color`、`1`）になります。
- **`listAdd`** は未使用の最小の正整数添字へ追加します。添字を指定して
  消すと**穴が残り**、詰め直しはされません。`deleteVar(listVar(name))`
  でリスト全体を消去しますが、素の `{name}` の削除では消えません。
- **`listRemove`** は一致する要素のうち**最初の1つだけ**（走査順）を
  消します。等値判定はフェーズ11の規則に従います。
- リストをテキストとして使うと `a, b and c` の形に連結されます
  （2要素なら `a and b`、1要素なら要素そのもの）。文字列の中で
  値が無い箇所は `<none>` と描かれます。未設定のスカラーや存在しない
  添字についても同様で、両ランタイム共通です。

ループの形： `loopTimes` は `loopValue()` を 1 から回数まで数え
（小数の回数は切り捨て）、`loopIndex()` は**持ちません**。Skript は
この位置の loop-index をパースエラーとして拒否し（"There's no loop
that matches 'loop-index'"）、プレイヤーループも同様です。添字を
持つのはリストループだけです。`loopRange` は両端を含み、開始が
終了より大きいと降順になります（`numbers from 4 to 2` は 4, 3, 2）。

`whileLoop` は反復のたびに条件を再評価します。ヘッドに置けるのは
葉条件か `not(葉条件)` のみです。`while` のヘッドは `if` のように
制御フローへ展開できず、Skript にはテキストの接続表現が存在しない
（フェーズ11の知見）ため、複合条件の `and`/`or`/`not` はビルダが
構築時に拒否します。

`wait` はトリガの残りを suspend します。後続の処理——囲んでいる
ブロックの残り、囲んでいるループの残りの反復、ループの後の文——は
指定時間の後に順序通り実行されます。Skript 側ではランタイム自身の
遅延挙動、エンジン側では Bukkit スケジューラ上の継続
（continuation）として同じ意味論を実装しています。量は小数も可
（`wait 0.5 seconds`）で、単位は `ticks` / `seconds` / `minutes` です。

## カスタム関数

`defineFunction(name, params, returnType, body)` で関数を定義し、
引数は `param(name, type, default?)` で宣言します。型は `number`、
`text`、`boolean`、`player`、`location`、`object` とその複数形
（`numbers`、`texts` など）に加え、単数形のみのゲームプレイ型
`block`、`item`、`entity` があります（後述の「ゲームプレイ
イベント」参照）。複数形の引数は最後尾に1つだけ
置けます（ビルダが強制します）。`returnType` は同じ型名のいずれか、
void 関数は `null` です。本体では引数とローカル変数を
`localVar(name)` / `localList(name)`（`{_name}`、`{_name::*}`）で
扱い、`returnValue(v)` で戻し、`stopTrigger()` で早期終了します。
呼び出しは式の `call(name, ...args)` と文の `callStmt(name, ...args)`
です。定義は Skript の `function` セクションとして出力され、
エンジンは IR から登録します。関数はコア言語であり、同じ
スクリプトが両ランタイムで動きます。

意味論（本家 Skript 2.17.1 へのプローブで裏取り。値の位置でも
文字列の中でも確認済み）：

- **解決はシグネチャ単位**。定義順・ファイル順は無関係で、定義
  より前の呼び出しも、ファイル間の呼び出しも可能です。名前は
  **大文字小文字を区別**します。オーバーロード（同名・引数型違い）
  は引数の型で振り分けられます。Skript は静的に（パース時に）
  解決するため、引数の個数違い・リテラルの型違い・型なし変数
  経由のオーバーロード呼び出しはパースエラーになります。
  エンジンは実行時に引数値の型で解決します（完全一致の型が
  `object` に勝つ）。引数型が静的に分かるプログラムでは観測
  される挙動は一致します。
- **変換は一切起きません**。実行時の型が引数の型と合わない値
  （`"5"` のような数値文字列を `number` 引数へ渡す場合を含む）
  は変換されず、引数が未設定のまま本体が実行されます（その後
  の挙動は本体側の意味論次第で、未設定の引数に対する算術は
  前述の「値なしオペランド」規則に従います）。値なしを明示的
  に渡した場合も同じで、デフォルト値は発動しません。
- **デフォルト値**は省略された末尾の引数にだけ適用されます。
  任意の式が書け、呼び出し時に、引数が1つも束縛される**前に**
  評価されます。グローバル変数は読めますが、引数は見えません。
- **ローカル変数は呼び出しごとの新鮮なフレーム**で、双方向に
  隔離されます。関数は呼び出し側の `{_x}` を見られず、関数内の
  書き込みが外へ漏れることもありません。入れ子の呼び出しも
  再帰（動作します）もそれぞれ独立したフレームを持ち、
  グローバル変数は通常通り共有されます。ローカルリストも
  グローバルと同様に使えます。関数本体には**イベント文脈が
  ありません**。Skript では関数内の `player` はパースエラーで、
  エンジンのコールフレームも空白から始まります。
- **戻り値の規律**。`return` には値が必須です（値なしの
  `return` は Skript ではパースエラー。早期終了には
  `stopTrigger()` を使います）。戻り値の実行時の型が宣言と
  合わない場合、呼び出しは**値なし**になります。値を返す関数が
  return せずに終わった場合も値なしです。複数形の戻り型は
  単一の値を1要素のリストとして包み、型の合わない要素を
  落とします。複数値の結果をスカラー変数へ代入すると値なし
  になります。リスト全体の代入（`set(localList("a"), someList)`）
  は対象を置き換え、反復順に 1..n へ詰め直します。
- **複数形の引数**は、ばらした値（`f(1, 2, 3)`）、リスト全体
  （`f({list::*})`）、単一の値のいずれでも受け取れます。本体の
  中ではローカルリスト `{_name::*}` として見えます。複数形の
  引数へ0個の値で呼ぶ呼び出しは解決されません。
- **関数内の `wait` は呼び出しを切り離します**。呼び出し側は
  wait が始まった瞬間に再開し、式としての呼び出しは値なしに
  なり、本体の残りは遅延の後に単独で実行され続けます。wait の
  後の `return` は Skript では**読み込みエラー**です（"A return
  statement after a delay is useless..."）。読み込める
  プログラムには現れない形であり、エンジンはこの形を受け
  入れて値を捨てます（最終的な意味論は同じです）。

`examples/functions.ts` がこれら全てを exercised し（再帰の
階乗、デフォルト値、オーバーロード、リストを返す関数への
複数形引数の合計、型不一致とスコープのデモ、切り離される
wait）、`examples/behavior/functions.behavior.ts` が両ランタイムで
同一の期待値を検証します。

## ゲームプレイイベント

ゲームプレイイベントはコア言語です。同じスクリプトが Skript
（出力された `.sk`）でもエンジン jar（独自の Bukkit リスナー
から発火）でも動きます。このスライスは**フィルタなしの形**
であり、Skript のフィルタ付き形（`on break of stone:`、
`on damage of player by zombie:`）と次のイベント群は次の節
です。汎用の `on click:`（右／左のペアでカバーします）と
ブロックダメージイベント（Skript 自身のドキュメントが
左クリックイベントを案内しています）は含みません。

イベント値（本家 Skript 2.17.1 へのプローブと振る舞いテストで
裏取り済み）：

- `eventBlock()` はイベント対象のブロックです。空への
  クリックにはブロックがありません。`locationOf(eventBlock())`
  でその位置が得られます。
- `eventItem()` は、**クリック**では手持ちアイテム、**設置**
  では置かれるアイテムです。**破壊**では手持ちの道具では
  なく、壊したブロックの**アイテム形**です（実測で確定：
  剣を持って草を掘っても `grass block` と報告されました）。
  空手のとき値は**存在せず**、文字列の中では `air` ではなく
  `<none>` と読めます。
- `toolOf(player())` は、プレイヤーの**メインハンド**の
  アイテムです。破壊の event-item が指していない
  「道具」そのものです。イベント値ではなく、
  プレイヤー値がある文脈ならどこでも手の内容を読みます。
  そのため破壊ハンドラでは両者を書き分けられます
  （振る舞いテストで確定：ダイヤの剣を持って草を掘ると、
  ブロックアイテムは `grass block`、道具は `diamond sword`
  と報告されます）。`offHandToolOf(player())` は
  **オフハンド**について同じ読み取りをします。空手では
  `air` のアイテムとして読めます（上の event-item が
  値なしになるのとは対照的です。本家の player-tool 式の
  意味論で、実 Skript でプローブ済み：両手とも `0 airs`、
  型は `air` と報告されます）。プレイヤーでない対象
  だけが値なしです。
- ダメージイベントでは `victim()` がダメージを受ける
  エンティティ、`attacker()` が与えたエンティティです。
  `attacker()` は環境ダメージ（落下、溶岩など）では値なし
  です。素の `player()` / `eventPlayer()` はダメージイベント
  では**定義されません**。Skript はパース時に弾き（"There's no
  player in an on damage event"）、エンジンも両方を未設定の
  ままにして倣います。
- `damageAmount()` はイベントの**現在**の量です。同じ
  ハンドラ内で先行した `setDamage()` の書き換えを反映します。
  量そのものはサーバーの計算です（素手の一撃が `1` になるのは
  攻撃チャージが満タンのときだけ）。エンジンも同じ Bukkit
  イベントを読むため、両ランタイムで同一になります。
- `damageCause()` は原因のテキストです。大半は小文字の名前
  （`fall`、`lava`）ですが、Skript の名前は機械的な変換では
  ありません。エンティティ攻撃は `attack` と印字され（実測で
  確定）、`FIRE_TICK` は `burning` と読めます。
- `cancelEvent()` は背後のイベントをキャンセル済みにします
  （ブロックは残り、ダメージは適用されません）。
  `uncancelEvent()` は同じイベント内での先行キャンセルを
  取り消します。キャンセルできない文脈では何もしません。
- エンティティをテキストとして使うと、プレイヤーは名前、
  それ以外は型名（`iron golem`、`slime`）として読めます。
  両ランタイム共通です。

ブロックとアイテムは値です。`typeOf(v)` は値の Skript 型名を
返し（`grass block`、`dirt`、`player`、`number` など。値なし
には型がありません）、`item("...")` リテラルとの比較が、
ブロックやアイテムの種類を判定する正式な方法です。ブロック
やアイテムをテキストとして使うとその名前として読めます。
関数の引数型と戻り型には単数形の `block`、`item`、`entity`
が使えます（このスライスでは複数形なし）。型付け上の注意点
が1つ、実 Skript の読み込みエラーで確定しています：
`typeOf(...)` が返すのはテキストではなく**型の値**です。
それを返す関数の戻り型は `object` でなければならず、文字列の
中では型の名前として印字されます。

`examples/gameplay.ts` がこれら全てを exercised します（土は
掘れず石は置けない＝どちらもキャンセル、クリックはブロック
とアイテムのラベル付きで通知、ダメージは報告され、名前付き
ボットの1体はキャンセル、もう1体は半減）。
`examples/behavior/gameplay.behavior.ts` が実ボットに掘る・
置く・クリックする・戦わせ、メッセージと結果のワールド状態
（ブロックが消えたか残ったか、体力が減ったか否か）の両方を
両ランタイムで検証します。

## イベントフィルタと追加イベント

フィルタ付きイベント形もコア言語です。クリック対象
エンティティの値と、取得・ドロップ・リスポーン・就寝／
起床の5イベントが加わります。以下はいずれも本家
Skript 2.17.1 で裏取り済みです。ヘッダの形はプローブ
スクリプトで読み込み時に、一致の仕方はサンドボックスの
モブ同士の戦闘を観察して、全セットは mineflayer 振る舞い
テストで両ランタイムとも確認しました。

**フィルタ。** イベントビルダーの末尾に付けるオプション
オブジェクトです。Skript のフィルタ付きヘッダは実行時の
式ではなくスクリプト本文中の**リテラルな型リスト**なので、
フィルタの値は型の**名前**を文字列（1つ、または配列）で
渡します。式にはしません（式にすると「ヘッダに変数が
書ける」という嘘の約束になります）。スロット名はヘッダ
の位置に対応します：

- `onBlockBreak(body, { block })` / `onBlockPlace` —
  `of` スロット： `on block break of stone or cobblestone:`
- `onDamage(body, { victim, attacker })` — `of` と `by`：
  `on damage of player by zombie:`。片側だけのフィルタも
  可能で、`by` のみ（`on damage by zombie:`）がパース
  できて動くことは API を許可する前にプローブで確定済み
  です。
- `onRightClick` / `onLeftClick(body, { block, entity, item })`
  — `on`（クリックしたブロック、またはクリックした
  エンティティ。両方の同時指定は拒否）と `with`（手の
  アイテム）： `on right click on villager:`、
  `on left click with stick:`
- `onPickup` / `onDrop(body, { item })` —
  `on pick up of wheat:`、`on drop of egg or compass:`

一致は Skript の型名で行います。`typeOf()` が印字し、
`item("...")` リテラルが使う名前（`stone`、`grass block`、
`zombie`、`player`）と同じです。リストはヘッダ内で
`a or b`、`a, b or c` と接続します。指定したスロットは
全て一致する必要があり、イベントに値が無いスロットは
決して一致しません（落下ダメージに攻撃者フィルタは
沈黙し、空へのクリックにブロックフィルタは沈黙します）。
エンジンも発火時に Bukkit の値へ同じ規則を適用します。

**クリック対象エンティティ。** `clickedEntity()` は右
クリックが相互作用したエンティティ（Skript の
`clicked entity`）で、ブロックや空へのクリックでは値を
持ちません。エンティティへの右クリックにはクリックした
ブロックはなく、手のアイテムは従来通り `eventItem()` です。

**追加イベント** はいずれも Skript の裸のヘッダと同じ
**プレイヤーの形**です。裸の `on pick up` / `on drop` が
モブでは発火しないことは実地で確認済みです（小麦を拾った
ゾンビでは明示形の `entity pick up` だけが発火しました。
この明示形はサブセット外です）。エンジンもプレイヤー
以外の取得をディスパッチしません：

- `onPickup` — プレイヤーがアイテムを拾う。
  `eventItem()` がそのスタックで、`cancelEvent()` で
  取得を拒否できます。
- `onDrop` — プレイヤーがアイテムを落とす。
  `cancelEvent()` でアイテムはインベントリに残ります
  （振る舞いテストは同じコンパスを2回投げて、一度も
  手を離れなかったことを証明します）。
- `onRespawn` — プレイヤーのリスポーン。**キャンセル
  不可**です（Skript は内部の `cancel event` をパース
  時点で拒否します）。
- `onBedEnter` / `onBedLeave` — `eventBlock()` がベッド
  です。就寝はキャンセル可、起床は不可です。

釣りは意図的に入れていません。Skript 2.17 は状態別の
サブイベント（cast / caught / hooked / bite / escape /
...）に分かれており、それ自体が設計面であることと、
bite のタイミングがランダムで振る舞いテストが不安定に
なるためです。死亡のフィルタ（`on death of zombie:`）も
入れていません。このサブセットの死亡イベントは
プレイヤー専用ですが Skript 側は全エンティティ対象で、
被害者フィルタを付けるとエンジン側が持ち得ない意味論を
約束してしまうためです。**更新（後述の「イベントの
一般化」）:** この2つの穴は埋まりました。死亡は
被害者フィルタ付きで全エンティティへ一般化され、
エンティティ取得／ドロップの明示形も入り、釣り一式も
ランダムな食いつきタイミングをテスト設計側で手なずける
形で入っています。

`examples/events2.ts` がこれら全てを使います（フィルタ
付きの破壊・設置・クリック・ダメージ報告、小麦だけを
拾い分ける取得、落とせないコンパス、リスポーンと就寝）
— `examples/behavior/events2.behavior.ts` が両ランタイムで
ボットを駆動して検証します。

## イベントのキャンセル状態とハンドラ優先度

上記と同様にコア言語です。同じスクリプトが Skript と
エンジンの両方で動きます。ここに書く内容はすべて実
Skript 2.17.1 に対してプローブで確認しました（優先度
ごとに1つずつ置いた6つのダメージハンドラを、キャンセル
するハンドラ有り・無しで実行し、未宣言ハンドラの
ディスパッチ位置を特定する専用プローブも行い、ヘッダー
の形はパースプローブで確認）。

**状態を読む。** `eventCancelled()` は条件
`event is cancelled` です（否定形はネイティブな
`event is not cancelled`。`the event is cancelled` という
綴りもパースできますが、出力はしません）。リーフ条件
なので、`ifElse`、`and`/`or`/`not` の論理、`whileLoop`
の先頭で使えます。読めるのは処理中のイベントの**現在の**
状態で、後述のディスパッチ規則により、具体的には
**ハンドラ開始時は false、自ハンドラが `cancelEvent()`
した後は true、`uncancelEvent()` で再び false** になり
ます。キャンセルできないイベント（リスポーン、ベッド
から出る）では常に false です（そこでも条件はパース
できます）。イベントの外（コマンド、関数本体）では
エンジンは false を返します。

**優先度。** すべてのイベントビルダーが `priority` を
受け付けます。フィルタ付きのビルダーはフィルタ
オブジェクトの中（`onDamage(body, { victim: "zombie",
priority: "highest" })`）、フィルタ無しのビルダーは
末尾のオプションオブジェクト（`onJoin(body, { priority:
"low" })`）です。値は `"lowest" | "low" | "normal" |
"high" | "highest" | "monitor"` のいずれかで、それ以外は
ビルダーが拒否します（Skript では未知のレベル名は
パースエラーです）。出力はヘッダーのサフィックス
`with priority <レベル>` で、必ず**すべてのフィルタ
スロットの後**に付きます（`on damage of zombie with
priority highest:`）。優先度を宣言しなければヘッダーは
従来どおりですが、そのハンドラがどこで実行されるかは
下記のディスパッチの注意を読んでください。`priority:`
というセクション行は存在しません（その形は本家でも
パースエラーです）。

**ディスパッチ順とスキップ規則。** 1つのイベントに
対するハンドラは、スロットごとに **lowest → low →
normal → high → highest → monitor** の順に実行され、
同じスロットの中では宣言順です（初回参加では
`firstJoin` と `join` のハンドラが1つの梯子を共有
します）。既存コードがその梯子のどこに位置するかを
決める、プローブで判明した注意点が1つあります。
**優先度を宣言していないハンドラは、normal ではなく
_high_ スロットで実行されます**（明示した `high` の
ハンドラと宣言順に交互に並びます）。normal スロットに
入るのは明示した `"normal"` だけです（直接プローブ:
未宣言ハンドラを明示 normal ハンドラより前に宣言して
も実行は後になり、明示 highest ハンドラよりは前に
なりました）。そして、イベントが一度キャンセル
されると、**後続のハンドラは一切実行されません**
（monitor も含みます）。ハンドラは、開始時点で
イベントがキャンセルされていない場合にだけ開始
します。これが実サーバーの安全地帯パターンの仕組み
です。キャンセルするガードを早い優先度（`lowest`、
`low`、`normal`。いずれも未宣言ハンドラが座る high
スロットより前）に置き、XP や報酬のハンドラを
`highest` か `monitor` に置けば、キャンセルされた
ヒットは報酬ハンドラに届きません。モジュールごとに
エリア判定を重ねる必要はなくなります（遅いハンドラ
の先頭で `eventCancelled()` を読んで止める形は保険
であり、穴を実際に塞ぐのはスキップ規則です）。例外
として考えるべきなのは `wait` で中断したハンドラ
本体です。残りのハンドラはそのハンドラの待機中に
開始します（Skript でも同様）ので、待機の後に発行
したキャンセルでは後続を止められません。

**記録された相違点（プラグイン間のインターリーブ）。**
Skript はトリガーごとに、その優先度で Bukkit リスナーを
登録するため、他のプラグインのリスナーとフェーズごと
に交互に実行されます。エンジンは自前のリスナー
（Bukkit の既定＝normal 優先度で登録）からハンドラ
一式をディスパッチします。優先度はスクリプトの
ハンドラ同士の順序を決め、スキップ規則はその集合の
内側で適用されます（イベントが早いフェーズの
プラグインによってキャンセル済みで届いた場合は、どの
ハンドラも実行されません）。ただし他のプラグインから
見ると、エンジンは normal フェーズの1リスナーとして
振る舞います。たとえば high フェーズでキャンセルする
保護プラグインは、high 優先度の Skript トリガーは
止められても、エンジンのハンドラは止められません。

`examples/priority.ts` がこれら全てを使います（順不同に
宣言した8つのダメージハンドラ、名前付きボットへの
ヒットをキャンセルする low 優先度のガード、未宣言
ハンドラの high スロット規則を固定するハンドラ）。
`examples/behavior/priority.behavior.ts` は被害者ごと
のブロードキャスト列そのものと、ガードされたボットの
体力が無傷であることを、両ランタイムで検証します。

## テキスト操作

テキストはコア言語です。同じスクリプトが Skript（出力された
`.sk`）でもエンジン jar でも動きます。以下の意味論はすべて
本家 Skript 2.17.1 へのプローブで裏取り済みで（開発ログ参照）、
いくつかは「当然」の挙動と異なります。

- `textLength(t)` は UTF-16 コードユニット数で数えます
  （絵文字は 2）。対象が値なしなら結果も値なし、空文字列の
  長さは 0 です。
- `substring(t, from, to)` は 1 始まりで両端を含みます。
  範囲は「適合」されます。`from` は 1 へ切り上げ、`to` は
  長さへ切り下げ、適合後の `from` が `to` を超えたら結果は
  **値なし**です（空文字列にはならず、交換もされません）。
  `firstChars(t, n)` / `lastChars(t, n)` は反対側の端を固定
  した同じ規則で、個数 0 以下は値なしです。`charAt(t, i)` は
  厳格で、1..長さ の範囲外は値なし、結果は UTF-16 コード
  ユニット1つです。
- `upperCase(t)` / `lowerCase(t)` は大小変換です。対象が
  値なしなら結果も値なし。単一テキストの操作は、本家の
  複数形と同じく、テキストのリストには要素ごとに適用
  されます。
- `splitText(t, delim[, caseSensitive])` は**リスト**を
  返します。区切りはリテラル照合（正規表現では決してない）
  で、既定は大文字小文字を**区別しません**。末尾の空要素は
  残り（`a,b,,c,` は5要素）、空文字列は空要素1つ、空の
  区切りは1文字ずつの要素＋末尾の空要素、対象が値なしなら
  要素なしです。結果はリスト機構と合成できます。リスト
  変数へ代入すれば、ループ（`loopIndex()` つき）、要素数、
  添字読みが、手で作ったリストとまったく同じに使えます。
  （本家では `size of` や `loop` も split を直接受けます
  —— split へのループには loop-index がありません —— が、
  本サブセットでは要素数とループはリスト変数の形に
  統一しています。）
- `joinText(list[, delim])` はリストの**テキスト要素**を
  連結します（プレイヤーは名前として数えます）。数値など
  テキストでない要素は変換されず**読み飛ばされます**
  （`(1, "x")` の結合は `"x"`）。残りが空なら値なし、
  既定の区切りは `""` です。split の結果を直接結合する
  こともできます: `joinText(splitText(t, str(",")),
  str("+"))`。
- `contains(a, b)` は、テキスト同士では大文字小文字を
  **区別しない**部分文字列テスト（空の部分は常に対象に
  含まれます）、リストに対しては比較規則による要素の
  所属テストです。`startsWith` / `endsWith` は大文字
  小文字を**区別します**。この非対称は本家自身のもので、
  プローブで固定しました。被演算子が値なしなら偽です。
  3つとも葉条件でネイティブの否定形を持つため、
  `whileLoop` の頭でも使えます。
- `replaceAllIn(var, find, repl[, caseSensitive])` /
  `replaceFirstIn(...)` はスカラー変数の持つテキストを
  書き換えます。リテラル照合で、既定は大文字小文字を
  区別しません。空の検索文字列は全ての隙間（all）または
  先頭（first）への挿入になります。対象が値なし・
  テキストでない場合は何もしません。
- 色: `colored(t)` / `formatted(t)` は `&` コード
  （`&x` の16進数並びを含む）と名前つき MiniMessage 式
  タグ（`<red>`、`<bold>`、閉じタグ、`<reset>`）を書式
  として解釈し、`uncolored(t)` / `unformatted(t)` は
  書式コードを**全て**取り除きます（色もスタイルも）。
  未知のタグ、対応のない閉じタグ、`&#RRGGBB` の形は
  リテラルのまま残ります。文字列リテラル自体も両ラン
  タイムで同じように解釈されます。Skript 2.17 は
  リテラルをテキストコンポーネントとして読み、エンジン
  はリテラルを § コード文字列へ変換します。一方、実行時
  に届く値（チャット文、計算された文字列）の生の `&` は
  `colored` / `formatted` を適用するまでそのままです。
  モデルの境界が1つあります。本家のテキストは
  コンポーネントで、エンジンのテキストは § コード文字列
  です。プレーンテキストの挙動とプレイヤーが目にする
  書式は一致し、解釈済みの値は等価な § リテラルと両
  ランタイムで等しくなりますが（サンプルの `/paeq` と
  `/fmteq` がこれを固定しています）、§ の文字数を数える
  式（色つきチャット文の長さなど）は、コンポーネントに
  数える § が存在しないため、異なり得ます。

`examples/text.ts` がこれら全てを exercised します
（`!` 接頭辞ルールつきの shout コマンド、文字の切り取り、
CSV の分割と結合、テキスト検査、置き換えデモ、paint 系
コマンド）。`examples/behavior/text.behavior.ts` が
観測可能な挙動を両ランタイムで検証します。

## アイテム・インベントリ・GUI

アイテム、インベントリ、GUI はコア言語です。同じスクリプトが
Skript（生成された `.sk`）でもエンジン jar でも動きます。
以下の意味論はすべて本家 Skript 2.17.1 へのプローブ
（コンソールプローブ＋mineflayer ボットによる実 GUI
クリック）で裏取り済みです（開発ログ参照）。

- **アイテム生成**は、任意のアイテム式への接尾辞の合成です。
  `withName(item, nameText)`、`withLore(item, ...lines)`、
  `withAmount(item, countExpr)` — `<item> named <text>`、
  `<item> with lore <a> and <b>`、`<count> of <item>`。
  これらのラッパーは実際のスタックを実体化します。素の
  アイテム名は新しいスタックになり、スタックは複製されて
  メタを書き換えられます。メタ付きスタックの `typeOf` は
  素材のままです。
- **アイテムの表示**: スタックは種別名で表示され、個数が
  2 以上では個数付きの複数形になります（`3 diamond
  swords`）。カスタム名があれば ` named <name>` が付きます。
  lore は表示されません。
- **等価性**: 2 つのスタックの比較は、種別＋個数に加えて、
  **両方**のスタックが持つメタ要素で決まります。名前付き
  スタックと無名スタックは等しく、異なる名前同士は異なり、
  名前の比較は大文字小文字を**区別**し、lore は行単位で
  比較されます。アイテム*リテラル*（や種別名）との比較は
  従来どおり種別のみなので、`eventItem() is item("stone")`
  はメタを無視します。
- **メタの読み取り**: `nameOf(item)` はカスタム名で、
  名前が無いアイテムでは値なしです（インベントリでは
  タイトル、プレイヤーでは名前）。`loreOf(item)` は lore の
  行をリストで返し、lore が無ければ値なしです。
  `amountOf(item)` はスタックの個数です（リスト値では
  リストのサイズ。本家の汎用 amount 式と同じ）。
- **メタの文**: `setItemName(var, text)`、
  `setItemLore(var, ...lines)`、`setItemAmount(var, count)`
  は、スカラー変数が保持するアイテムを書き換えます
  （`set name of {v} to ...` など）。変数が素の種別名を
  保持していれば先に実体化され、アイテム値を持たない
  変数は変更されません。`giveItem(player, item)` は
  アイテム式（メタ込み）をプレイヤーへ渡します。
- **手持ちアイテム**: `toolOf(player)` はプレイヤーの
  メインハンドのアイテム（`tool of %player%`、本家の
  player-tool 式）、`offHandToolOf(player)` はオフハンドの
  アイテムです（`offhand tool of %player%`）。空手では
  `air` のアイテムとして読めます（道具の式は空手でも
  値を持ち、event-item は値なしになります）。プレイヤー値が
  ある文脈で手の内容をそのまま読み、ブロック破壊では
  メインハンドが掘っている道具を返します（`eventItem()` は
  壊したブロックを返す。ゲームプレイイベントの節を参照）。
- **値としてのインベントリ**: `chestInventory(rows[,
  title])` は新しい仮想チェストインベントリを作ります
  （行数は 1..6 に丸め）。プレイヤーとは独立に存在します。
  `currentInventoryOf(player)` はプレイヤーが開いている
  インベントリ（何も開いていなければ本家同様に本人の
  クラフトインベントリ）、`eventInventory()` は
  インベントリイベントのトップインベントリです。
  `slotItem(inv, slot)` は 0 始まりのスロットを読み
  （空スロットは値なし）、`setSlot(inv, slot, item)` は
  書き込みます。インベントリとしてプレイヤーを渡すと
  本人のインベントリを指し、値なしのアイテムはスロットを
  空にします。`openInventory(player, inv)` はインベントリ
  値を開き、`openGui(player, rows[, title])` はチェスト
  GUI を作って開く一文形式、`closeInventory(player)` は
  表示を閉じます。
- **インベントリイベント**: `onInventoryClick` は、スクリプト
  GUI でもバニラのコンテナでも、全てのインベントリ
  クリックで発火します。中では `eventItem()` がクリック
  されたスロットのアイテム（空スロットは値なし）、
  `eventInventory()` がビューのトップインベントリ、
  `clickedSlotIndex()` がクリックされたインベントリ内の
  スロット番号（自分の下部インベントリのクリックは
  その左上から数える）、`clickedRawSlotIndex()` がビュー
  全体での番号です。中の `cancelEvent()` が GUI の標準的な
  守りで、キャンセルされたクリックは何も動かしません。
  `onInventoryClose` は、スクリプトからでもプレイヤーの
  操作でも、表示が閉じた時に発火します。

テキストと同様のモデル境界が1つあります。表示名と lore は
Skript ではコンポーネント、エンジンでは § コード文字列で、
メタの境界で変換されます。プレイヤーに見える装飾は一致し、
コード無しの名前の読み取りも一致します。

`examples/gui.ts` がこれら全てを使います。メタの文で
名前と lore 付きの剣を作る `/gem`、読み戻す `/geminfo`、
クリックハンドラに守られたチェスト GUI `/menu` です。
`examples/behavior/gui.behavior.ts` はボットに両ランタイムで
全フローを実演させ、キャンセルされたクリックで GUI の
ダイヤがボットのインベントリに入らないことまで確認します。

このスライスの対象外（記録済み、今後の候補）:
インベントリのドラッグイベント（クリックをキャンセルした
GUI でもドラッグはアイテムを動かし得ます）、スロットへの
add/remove 形式、カーソルスロット、名前・lore・個数以外の
メタ（エンチャントなど）。

## ワールド操作と周期イベント

ブロック、位置、ワールドの状態、周期トリガはコア言語
です。同じスクリプトが Skript（出力された `.sk`）でも
エンジン jar でも動きます。以下の意味論はすべて本家
Skript 2.17.1 に対してプローブで裏取りしました
（コンソールプローブ複数ラウンド。詳細は開発ログ）:

- **値としてのブロックと位置**: `blockAt(loc)` は
  位置のブロック（`block at %location%`）、
  `setBlockAt(loc, item)` はアイテムのマテリアルを
  その位置に書きます（`set block at ... to ...`。
  air アイテムでブロックが消えます）。ブロックの
  印字は `'<種別>' at <cx>, <cy>, <cz> in world
  '<名前>'` で座標は**中心**であり、ブロックの
  `locationOf` は中心位置です。エンジンも両形式を
  再現します。
- **位置**: `location(x, y, z)` はサーバーのメイン
  ワールドに位置を作り、`location(x, y, z, world)`
  はワールド式を取ります。印字は `x: <x>, y: <y>,
  z: <z>, yaw: <yaw>, pitch: <pitch> in
  '<ワールド>'` です。`xOf` / `yOf` / `zOf` は
  座標を読みます（`x-coordinate of ...`）。
  `offsetLocation(loc, dx, dy, dz)` はベクトルで
  位置をずらします（`%location% ~ vector(...)`）。
  成分は式です。
- **相対ブロック**: `relativeBlock(target,
  direction[, amount])` はブロックまたは位置から
  方向へ進んだブロックです。`above`、`below`、
  `north`、`south`、`east`、`west`（絶対方向）と
  `front` / `behind`（向き相対: 対象位置の向きに
  従い、ブロック自体の位置は南向きです）。出力
  形式は方向ごとに異なります（`block above %t%`、
  `block 2 north of %t%`、`block in front of %t%`、
  `block behind %t%`。すべてプローブ済み）。
- **ワールド**: `world("name")` は名前による
  ワールドです（未知の名前は無値）。`worldOf(target)`
  は——このフェーズでコア言語になりました（MundoSK
  スライスではエンジン内蔵でした）——プレイヤー・
  位置・ブロックのワールドを読みます。
- **ワールドの時計**: `worldTime(world)` は
  ワールドの時計を `H:MM` テキストで読みます
  （`time in %world%`）。0 ティックで `6:00`、
  6000 で `12:00`、18000 で `0:00` です。
  `setWorldTime(world, value)` で設定します。値は
  `clockTime("13:00")` リテラルか、時計テキストを
  運ぶ式（`worldTime` を入れた変数の往復も
  プローブ済み）です。本家の timespan 形式は
  パースできますが効果を裏取りできなかったため、
  意図的に対象外とします。時刻の算術もサブセット
  には含みません。
- **天気**: `worldWeather(world)` は `clear`、
  `rain`、`thunder` を読み（`weather in %world%`）、
  `setWorldWeather(world, name)` はリテラル名で
  設定します。天気の値は `weatherType("rain")`
  リテラルと比較します——出力は**裸**の形式
  （`is rain`）です。引用符付きテキスト形式は
  パースできますが決して等しくならず、プレーンな
  テキストは変換されません（テキスト変数からの
  設定は本家でも無言で無効です。いずれも
  プローブ済み）。
- **周期イベント**: `every(amount, unit, body)` は
  周期トリガです（`every 3 seconds:`）。量は数値
  **リテラル**のみです（式の周期は本家のパーサが
  弾きます）。分数も使えます（`every 2.5 seconds`
  は周期通りに発火）。単位は `ticks` / `seconds` /
  `minutes`。初回発火はロードから1周期後で、
  リロードでスケジュールは再アンカーされます
  （時刻付きログでプローブ済み）。本体には
  イベント文脈がありません（関数本体と同様）。

本家側のクセがこの一族（と変数に対する `typeOf`）
に当てはまります: Skript 2.17.1 はこれらの複合式を
文字列補間の中ではパースしません——値の位置専用
です。変数に代入してから変数を補間してください
（サンプルはそうしています）。エンジン側にこの
制限はありません。

`examples/world.ts` が一通りを exercise します——
3秒ハートビートの周期トリガ、`/wstat` / `/wday` /
`/wnight` / `/wcalm` / `/wstorm` のワールド状態
コマンド、`/wpos` の座標読み返し、`/wbuild` と
`/wraze` の実ブロック設置と除去——そして
`examples/behavior/world.behavior.ts` が両
ランタイムでボットに全フローを駆動させ、
ハートビートの周期測定も含みます。

このスライスの対象外（記録済み、今後の候補）:
*エンティティ*からの向き相対オフセット（位置の
形式はプローブ済みで収録。エンティティの向きは
実機での向きプローブ設計が別途必要です）と、
ワールド時刻の算術です。

## ワールドペイント: 形状とフィル

_形状 × フィル_ として合成する一括ワールド
構築です。形状の値はブロック位置の集合を表し、
フィルの値は各位置に置く素材を決め、`paint`
文が領域全体を **エンジンの1つの操作として**
書き込みます——ブロックごとの文の羅列には
決してなりません。このファミリーは
**エンジン専用**（アドオンスライスと同様の
エンジンビルトイン）です。一括の単一操作という
意味論と、後述するシード付き・位置のみで決まる
素材選択は Skript テキストでは表現できないため、
エミッタはこれらの kind で例外を投げ、使用した
スクリプトは IR のみでデプロイされ、Skript
モードのデプロイではスキップされます。形状と
フィルは実行時のみの値（データソースと同様）
で、変数に保存して再利用できますが、再起動を
またいで永続化されることはありません。

形状（位置はブロック位置です。ロケーションは
そのブロック座標を与え、最初のロケーションの
ワールドが形状全体の基準になります）:

| TS ビルダー | 形状 |
|---|---|
| `cuboid(from, to)` | 2つの隅のロケーションの間の全ブロック（含む、隅の順序は不問） |
| `sphere(center, radius)` | 中心ブロックからの整数オフセットが dx²+dy²+dz² ≤ radius² を満たす全ブロック |
| `cylinder(center, radius, height)` | 中心ブロックの上で dx²+dz² ≤ radius²、その Y から `height` 層（層数: 四捨五入、最低1） |
| `blockLine(from, to)` | 2つのロケーションを結ぶ線分上のブロック。主軸方向にステップし各軸で丸めるため線はつながり、両端を含みます |

負の半径、または円柱の高さが0以下では、何も
描かれません。

フィル（アイテム式は `setBlockAt` と同じ規則——
スタックの型、型名、ブロックの型——で素材に
解決されます）:

| TS ビルダー | フィル |
|---|---|
| `uniformFill(item)` | そのアイテムの素材を全位置に |
| `mixFill([[item, weight], ...], seed?)` | 位置ごとに、累積ウェイトで1つのエントリを選択 |
| `noiseFill(base, spot, { scale?, amount?, seed? })` | シード付きバリューノイズが高い位置に spot の素材、それ以外に base の素材 |

- **決定性が契約です**: ミックスとノイズの
  選択は (seed, x, y, z) の純粋な関数
  （splitmix64 系の位置ハッシュ）なので、
  同じ形状に同じフィルで塗り直すと、どの実行
  でもどのサーバーでも同じワールドが正確に
  再現されます。パターンはワールドの絶対座標に
  依存します。同じ形状を別の場所に描くと、
  異なる（が再現可能な）パターンになります。
  シードはビルダーレベルの数値（既定 0）で、
  エンジン側で整数に切り捨てられます。
- **ミックス**: ウェイトは相対値（選択時に
  正規化）で、正である必要があります。素材に
  解決できないアイテムのエントリはフィルの
  評価時に除外され、1つも残らなければフィルは
  値なしとなり、paint は何もしません。
- **ノイズ**: 3D バリューノイズ——`scale`
  ブロック（既定 4）のセル格子上のハッシュ値を、
  smoothstep の重みで三線形補間します。ノイズ値
  が `1 - amount` に達した位置が spot の素材に
  なります。`amount`（既定 0.5）は spot の
  おおよその被覆率です（バリューノイズは一様
  分布ではないため）。amount 0 では全て base、
  1 では全て spot になります。素材に解決
  できない側の位置は、そのまま残ります。

文: `paint(shape, fill)` は形状の全位置を
書き込みます。`paint(shape, fill, { replace:
item })` は、現在そのアイテムの素材を持って
いる位置だけを書き込みます——そして replace の
アイテムが素材に解決できない場合、制限なしの
paint に劣化するのではなく、文全体が何もしなく
なります。既に選ばれた素材を持っているブロック
はそのまま残り、書き込みには**物理更新を適用
しません**（置いた砂利は落ちず、水は書き込み
自体では流れません）。位置のブロックを読むと、
`blockAt` と同様にそのチャンクが読み込まれます。

`examples/paint.ts` はプレイヤーの足元を基準に
このファミリーをコマンドから駆動します——
ノイズ混合とウェイト混合の床、replace 制限付き
の再塗装をする壁、上昇する線、球と円柱——そして
`examples/behavior/paint.behavior.ts` がエンジン
のもとで実サーバー相手に形状とシードの再現性を
検証します。

## プレイヤー状態とエフェクト

プレイヤー／エンティティの状態の読み書き、
ポーション効果、召喚・ドロップ・サウンドの各
エフェクトはコア言語です。同じスクリプトが
Skript（出力された `.sk`）でもエンジン jar でも
動きます。以下の意味論はすべて本家 Skript
2.17.1 に対して、サーバーコンソール経由の NBT
真値で裏取りしました（詳細は開発ログ）:

- **単位——最重要の事実**: 体力と最大体力は
  **ハート**（Bukkit の HP の半分）です。満タンの
  プレイヤーは `10` と読み、端数は正確です
  （6.3 ハート = 12.6 HP）。空腹度は**モモ**
  （食料ポイントの半分）、満腹度（saturation）は
  **無換算**です。エンジンも同じ ×2 / ÷2 換算を
  行うため、両ランタイムで数値が一致します。
- **状態の式**: `healthOf(t)`、`maxHealthOf(t)`
  （生物エンティティ一般）、`foodLevelOf(p)`、
  `saturationOf(p)`（プレイヤーのみ）、
  `gameModeOf(p)`（モード名をテキストで）、
  `experienceOf(p)`、`levelOf(p)`。
- **状態の書き込み**: `setHealth`、
  `setMaxHealth`、`setFoodLevel`、`setSaturation`、
  `setExperience`、`setLevel`——いずれも式自身の
  単位で書きます。プローブ済みの挙動: 体力の
  書き込みは最大値でクランプされ、`0` で死亡
  します。空腹度の書き込みは整数ポイントへ
  丸めます（6.3 モモ → 13 ポイント）。満腹度は
  空腹度でクランプされません。最大体力の設定は
  属性の base を書き換え、現在の体力には触り
  ません。レベルの設定は進捗割合を保持します
  （総量 47 → レベルだけ 2 に設定 → 総量は 21 と
  読みます）。経験値の設定は総量を正確に設定し、
  レベルと進捗を再導出します。`heal(t)` は
  全回復、`heal(t, n)` は n ハート回復です。
  汎用チェンジャ `addTo(expr, n)` /
  `removeFrom(expr, n)` は体力・空腹度・経験値・
  レベルの各式を対象にします（`add 41 to
  experience of player`）。
- **ゲームモード**: フェーズ18の天気と同様、値は
  プレーンなテキストと相互変換しません——引用符
  付きテキストとの比較は本家ではパースエラーに
  なり、テキスト変数からの設定は無言で無効です
  （いずれもプローブ済み）。そのため
  `gameModeOf` は表示用の名前を返し、
  `setGameMode(p, "creative")` は検証済み
  リテラルを取り、比較は `gameModeType("creative")`
  リテラル（**裸**で出力、`is creative`）を使い
  ます。
- **経験値**: `experienceOf` はレベル＋進捗から
  計算した**総量**です——生の総量フィールドは
  スクリプト書き込みで古くなるため使いません
  （プローブ済み）。観測可能性の注意: 1つの
  トリガが経験値を複数回書くと、サーバーは
  最終状態だけをクライアントへ同期します。
  そのため振る舞いテストでは中間の総量を
  スクリプトの読み戻しで assert します。
- **ポーション**: `applyPotion(t, type[,
  {level, durationSeconds}])` と
  `removePotion(t, type)`。種別は検証済みの
  表示名です（`"speed"`、`"fire resistance"`、
  `"instant health"` など——バニラ全31種を
  プローブ済み、`swiftness` は speed の別名）。
  本家での既定は、エンティティの NBT で
  プローブした通り **レベル1** と持続 **30秒**
  （600 ティック）です。本家には **全解除の
  形式がありません**（候補3形ともパース不能
  でした）。そのため提供せず、解除は1種ずつ
  行います。即時回復・即時ダメージも通常の
  種別ですが、この Paper 版では適用した即時
  効果が持続する効果エントリとしても残る
  というプラットフォーム側のクセがあります
  （NBT で観測）。エンジンも同じ Bukkit 呼び出し
  を使うため挙動が一致します。
- **召喚**: `spawnEntity(type, at[, count])` は
  位置またはエンティティの場所に召喚します。
  `lastSpawnedEntity()` は直近の召喚を読み
  （`last spawned entity`）、`typeOf` で種別名が
  印字できます。
- **ドロップ**: `dropItem(itemExpr, at)` は
  アイテム値の式（フェーズ17のスタックが合成
  でき、メタも含みます）を位置または
  エンティティの場所に落とします。
- **サウンド**: `playSound(name, at)` は
  レジストリ名（`"block.note_block.pling"`）の
  音を位置またはエンティティで鳴らします。
  本家は名前をサウンドレジストリで解決します
  （パケットはレジストリ ID を運びます。
  ワイヤレベルでプローブ済み）。エンジンも同様
  です。**音量・ピッチのオプションは意図的に
  ありません**: 音量の形式は本家でパースできず、
  ピッチの形式はパースできてもワイヤ上の
  ピッチを変えません（0.5 でも 2 でも 1 で
  到着しました）。

`examples/state.ts` が一通りを exercise します
——`/ststat` の状態読み戻し、`/stset`、
`/stheal`、`/stgm` のゲームモード往復、`/stxp`
と `/stxpfrac` の経験値フロー、`/stmax`、
ポーション三点セット `/stfx` / `/stpoison` /
`/stcure`、`/stinstant`、`/stspawn`、`/stdrop`、
`/stsound`——そして
`examples/behavior/state.behavior.ts` が両
ランタイムでボットに全フローを駆動させ、
ボット自身の体力・空腹度・ゲームモード・
経験値レベル・視認エンティティ・インベントリ・
受信サウンドパケットで assert します。

このスライスの対象外（記録済み、今後の候補）:
複数種別を1文で付与すること（本家は `and`
リストをパースしますが、サブセットは1文1種別
とします）、ポーション全解除の形式（本家に
存在しません）、最大体力と満腹度に対する汎用
add / remove チェンジャ（この2式については
未プローブ）、プレイヤー以外のエンティティに
対する空腹度・ゲームモード（本家の型体系では
プレイヤー専用）です。

## コマンド定義

コマンドは型付き引数を任意個まで取れ、`permission` / `usage` /
`aliases` のセクション要素も備えます。コア言語として Skript
モードとエンジン jar で同一意味論です。以下の挙動はすべて本家
Skript 2.17.1 へのプローブで裏取りしました（開発ログ参照）。
本家はコマンドを **Brigadier** で登録するため、引数の失敗は
バニラ Brigadier のメッセージとなり、本体は実行されません。
エンジン側のマッチャもこれを正確に再現します。

- **引数**: `command(name, [cmdArg(type, optional?), ...], body, options?)`。
  型は `"text"` / `"player"` / `"offlinePlayer"` / `"integer"` /
  `"number"` / `"boolean"` / `"item"`。本体では `argument(n)`
  （1始まり）でパース済みの値を読みます。従来の単一引数形式は
  そのまま使えます。
- **パース**: `player` 引数はオンラインのプレイヤーをフルネームで
  解決します（大文字小文字を区別しない）。オフライン・未知の名前は
  `No player was found` で失敗し（コンテキスト行なし）、セレクタ
  （`@a` 等）は拒否されます。`integer` は Brigadier の long
  （`Expected long` / `Invalid long '...'`）、`number` は double
  （`Expected double`）、`boolean` は小文字の `true` / `false`
  のみ。`item` 引数は1トークンの名前空間付きアイテム ID
  （`diamond_sword`、`minecraft:diamond_sword`）で、未知の ID は
  `Unknown item 'minecraft:...'` で失敗します。`offlinePlayer` は
  **任意の名前**を受け付けます。`text` 引数は1トークン、末尾位置では
  行の残り全部を取り込みます。不正な値、余分なトークン
  （`Incorrect argument for command`）、必須引数の不足はいずれも
  呼び出しを失敗させます。フィードバックはチャットメッセージ
  **1件**で、理由＋改行＋`<--[HERE]` コンテキスト行の形です。
- **省略可能引数**（`[<type>]`）: 省略すると値なし、与えた値は検証
  されます。必須引数の前にある省略可能引数は**バックトラック**し、
  `[<integer>] <text>` に対して入力 `hello` はテキストとして
  読まれます。**引数のデフォルト値は提供しません**: 本家の
  `[<type> = <expr>]` 形式はロードできるものの壊れており
  （プローブ確認: 値を渡すとディスパッチ失敗、省略しても
  デフォルトは適用されない）、サブセットには入れません。
- **セクション**: `permission`（持たない送信者はコマンドを
  アドレスできず、失敗表示は未知のコマンドと同じ形。OP と
  コンソールは通過）、`usage`（そのまま送信される。表示されるのは
  引数不足の失敗のときだけ）、`aliases`（追加の名前。先行スラッシュ
  の有無はどちらでも可）。**`permission message` は提供しません**:
  本家で非推奨化され、実際には届きません（プローブ確認）。

`examples/commands.ts` が全体を網羅します — `/cpoke`、
`/croll`、`/citem`、`/ctell`、`/cmix`、`/coff`、`/cadmin`、
`/cuse`、`/calias`（＋`/ca2`、`/ca3`）— そして
`examples/behavior/commands.behavior.ts` が2体のボットで両
ランタイムを通し、失敗メッセージの文面と権限ゲート（権限を
持たない送信者からの見え方）まで確認します。

意図的な相違と見送り（記録済み）: エンジンはスペース区切りの
トークン単位でマッチするため、Brigadier リーダがトークン途中で
止まるケース（数値にゴミが融合した入力）は部分パースではなく
トークン全体のエラーになります。タブ補完はエンジンモードでは
プラットフォーム既定（本家は Brigadier の候補提示）。
`executable by` / `prefix` / クールダウンのセクションと、
式で型を決めるカスタム引数は今回の対象外です。

## 画面表示エフェクトとボスバー

タイトル、アクションバー、ボスバーはコア言語として、
Skript でもエンジン jar でも同一意味論で動きます。以下の
挙動はすべて本家 Skript 2.17.1 に対して、クライアントの
パケットを生で捕捉して裏取りしました（開発ログ参照）。

- **タイトル**: `sendTitle(target, text, options?)`。
  `options.subtitle` と、リテラルの時間指定 `fadeIn` /
  `stay` / `fadeOut`（各 `{ amount, unit }`、小数可）。
  時間指定の尾部は対象の **後ろ** に来ます —
  `... to player for 5 seconds with fadein 1 second and
  fade out 1 second`（`for` を `to` の前に置くと本家でも
  パースエラー）。ワイヤ挙動: 時間指定が **無い** 場合は
  時間パケット自体が送られず（クライアントは前回の時間を
  維持）、**いずれか** を指定すると時間パケットが1つ
  テキストパケットに先行し、未指定部分は既定値
  **フェードイン10 / 表示70 / フェードアウト20 ticks** で
  埋まります。パケット順序は 時間 → サブタイトル →
  タイトルの順。タイトルのみの送信ではサブタイトル
  パケットは送られず、その逆も同様です。
  `sendSubtitle(target, text, timingOptions?)` は
  サブタイトルのみの形式。`clearTitle(target)` は
  タイトルを消し、`resetTitle(target)` は時間設定も
  リセットします（リセットフラグ付きの1パケット）。
  タイトルのテキストは任意の式で、チャットメッセージと
  同じく文字列化されます。
- **アクションバー**: `sendActionBar(target, message)` —
  1パケットのみで、時間の概念はありません。
- **ボスバー**（Skript 2.16 からコア）: 作成式
  `bossBar({ title?, color? })` がバーの値を生成します
  （新規バーはタイトル空、進捗1、白、無地スタイル —
  すべて追加パケットから読み取り）。`setBossBarTitle` /
  `setBossBarColor`（リテラル名: pink、blue、red、green、
  yellow、purple、white）/ `setBossBarProgress` が
  プロパティを書き換えます。進捗は **0..1 の割合** で、
  本家はクランプします（50 を書くと 1 と読み戻される。
  手書き Skript のパーセントリテラルはこの割合を
  100で割ったもの）。`addBossBarViewer` /
  `removeBossBarViewer` が閲覧者を管理し、
  `bossBarTitleOf` / `bossBarProgressOf` がプロパティを
  読み戻します。**バーは保存できません**: 永続変数への
  格納は本家ではロードエラー（"a boss bar cannot be
  saved"）になるため、バーはローカル変数に置きます。
  エンジン側はエラーの代わりに値をメモリ上に保持し、
  変数の保存時に落とします（記録済みの相違）。

- **キードボスバー、スタイル、フラグ、セクション**
  （フェーズ24、2.17.1 でプローブ）:
  `keyedBossBar(key, { title?, color? })` はサーバーの
  永続ボスバーストレージにバーを作成します。作成の評価は
  そのキーに保存された既存のバーを新しいバーで **置き換え**
  ます（タイトル空、進捗 **0** — バニラのカスタム
  ボスバーの初期値）。`keyedBossBarOf(key)` はキーで
  取得し、存在しないキーは値なしで、バーを作ることも
  ありません。キーは完全な名前空間キーです（裸のキーは
  `minecraft:` 名前空間。使える文字は小文字・数字と
  `.` `_` `-`、キー部分はさらに `/`）。無効なキーは
  本家では実行時エラーとなり、こちらでは値なしに
  なります。`deleteKeyedBossBar(key)` は保存された
  バーを削除します（存在しなければ静かな no-op）。
  キードバーは **保存できます**: 永続変数にはキーが
  記録され、読み込み時に解決されます。再起動後も
  残りますが、進捗だけはバニラのストレージが保存
  しないため 0 と読み戻されます。`bossBarKeyOf(bar)` は
  `namespace:key` の全文を読みます（無名バーでは
  未設定）。`setBossBarStyle(bar, style)` はスタイル
  リテラル（`solid`、`6 notches`、`10 notches`、
  `12 notches`、`20 notches`）を書き、
  `bossBarStyleOf(bar)` は `solid` または `N segments`
  と読み戻します（本家の非対称な綴り）。
  `setBossBarFlag(bar, flag, enabled)` のフラグは
  `darkenSky` / `createFog` / `playBossMusic` で、
  make / make-no-longer 形式を出力します。条件
  `bossBarDarkensSky` / `bossBarCreatesFog` /
  `bossBarPlaysBossMusic` が読み取りに使えます
  （新規バーは全フラグ off）。
  `createBossBarSection(target, body, { key?, color? })`
  はセクション作成形式で、本体は新しいバーを
  `eventBossBar()`（`event-bossbar`）として参照し、
  対象変数への束縛は本体の実行後に行われます。
  セクションのヘッドには色は使えますがタイトル句は
  ありません（ドキュメントのキード＋タイトルの
  セクション例は本家でパースできません — タイトルは
  本体で設定します）。記録事項として再現しないもの:
  キード **作成** 式の削除は本家がクラッシュする
  （ClassCastException）ため、削除はこちらでは取得
  形式を出力します。セクション内では外側イベントの
  `player` が見えない点は本家と同じです。

`examples/display.ts` が全体を exercise します — 参加時の
時間指定付きタイトル＋サブタイトルとアクションバー、
`/dtplain`、`/dtstay`、`/dtsub`、`/dtclear`、`/dtreset`、
`/dbar` の各コマンドと、`/dbshow` / `/dbfresh` のボスバー
ライフサイクル — そして
`examples/behavior/display.behavior.ts` が両ランタイムで
クライアントの実際のタイトル / アクションバー /
ボスバーのパケットを検証します。

`examples/bossbar.ts` がキードバーの一連を `/bossbar`
コマンドとして実行し、
`examples/behavior/bossbar.behavior.ts` が両ランタイムで
ナレーション列（作成 / リセット / スタイル / フラグ /
キー / セクション / 変数保存 / 削除）と表示バーの
ワイヤパケットを検証します。

意図的な見送り（記録済み）: タイトル対象の
複数オーディエンス（本家は `%audiences%`。本サブセットの
送信系は他と同様に単一プレイヤー対象）。

## イベントの一般化： 死亡、エンティティ取得／ドロップ、釣り

v0 のイベント群はプレイヤー中心の形から始まりました。
本節ではそれを本家の形へ一般化します。全てコア言語
（TS API / .sk エミッタ / jar エンジンの3経路で同一
意味論）で、以下の規則はすべて本家 Skript 2.17.1 への
プローブで裏取りしてあります（ヘッダのパースはプローブ
スクリプトで、実行時のマッチングはモブ・釣りボット・
コンソールのダメージをサンドボックスで駆動して確認）。

**死亡は全ての生物エンティティ対象になりました。**
`onDeath(body)` はあらゆるエンティティの死亡で発火し、
「イベントフィルタ」の系統の被害者フィルタ
`onDeath(body, { victim })`（`on death of zombie or
skeleton:`）を取ります。内部では `victim()` が死んだ
エンティティ、`attacker()` は**最後のダメージ原因**の
加害者（その原因がエンティティ攻撃だった場合）です。
加害者は*あらゆる*エンティティで、プローブ済みです。
アイアンゴーレムに倒されたゾンビでは加害者は
`iron golem`、コマンドキルでは加害者なし、プレイヤーの
剣キルでは `player` と読みます。正直な制限が3つあり、
いずれもプローブ済みです。ヘッダに**加害者フィルタは
ありません**（`on death … by player:` は本家でもパース
できないため提供しません）。`player` は本家の死亡
イベントには存在しません（そちらではパースエラーに
なるので `victim()` を使ってください。被害者が
プレイヤーの場合、エンジンはプレイヤーの値も埋める
ため v0 のハンドラはそのまま動きます）。そしてこの
イベントはどちらのランタイムでもキャンセル不可です
（内部の `cancelEvent()` は既定の no-op）。

**エンティティ取得とドロップ。** `onEntityPickup(body,
{ item })` と `onEntityDrop(body, { item })` が明示形
（`on entity pick up of wheat:`、`on entity drop of
egg:`）で、第16弾の `{ item }` フィルタ付きです。新値
`eventEntity()` はイベントの主体エンティティです。
対象範囲はプローブ通りに2形で異なります。エンティティ
取得は**全ての**取得者（プレイヤーを含む）で発火し
（プレイヤーの取得では通常形*と*本形の両方が発火し、
`eventEntity()` = そのプレイヤー）、エンティティ
ドロップはプレイヤーでは決して発火しません
（プレイヤーの投げは通常形のみ — 土台の Bukkit
イベント自体が別物です）。エンティティドロップでは
`droppedItemEntity()` がドロップされたアイテム
エンティティ、`itemOfEntity(entity)` がそのスタック
（`item of event-dropped item`）で、スタックは
`eventItem()` でもあります。どちらもキャンセル可です。

**釣り**は1つのイベントではなく状態別サブイベントの
一式です。本家に汎用の `on fishing:` は存在しません
（パースエラー）。Bukkit の釣り状態ごとにサブイベント
があり、全状態で発火する状態変化イベントが1つあります。

| ビルダ                 | ヘッダ                     | 状態名              |
| ---------------------- | -------------------------- | ------------------- |
| `onFishCast`           | `on fishing line cast:`    | `fishing line cast` |
| `onFishApproach`       | `on fish approaching:`     | `lured`             |
| `onFishBite`           | `on fish bite:`            | `bite`              |
| `onFishCaught`         | `on fish caught:`          | `fish caught`       |
| `onEntityHooked`       | `on entity hooked:`        | `entity caught`     |
| `onHookInGround`       | `on bobber in ground:`     | `bobber in ground`  |
| `onFishEscape`         | `on fish escape:`          | `fish escape`       |
| `onFishReelIn`         | `on fishing rod reel in:`  | `reel in`           |
| `onFishingStateChange` | `on fishing state change:` | （全て）            |

状態名は `eventFishingState()` が表示する文字列で、
`fishingState("bite")` が対応リテラルを作ります
（未知の名前はビルド時に拒否）。状態変化ハンドラは
`if equals(eventFishingState(), fishingState("bite"))`
のように分岐できます。`fishingHook()` はウキで、型名は
`fish hook` と表示されます。2つの「釣れた」状態では
`eventEntity()` が釣れたものです。魚の場合はアイテム

## 値としてのタイムスパン

タイムスパンは、3つのパス(TS API、.sk エミッタ、jar エンジン)すべてで第一級の値型となった。すべての規則は、実物の Skript 2.17.1 に対して検証済みである。タイムスパンはミリ秒単位の整数値であり(1か月は30日、1年は365日)、リテラルビルダー `timespan(amount, unit)` はティック、秒、分、時間、日、週、月、年の8単位すべてをカバーし、量を最も近いミリ秒へ丸める。

表示では、年から分までの単位で貪欲に分解を行い、分未満の余りは繰り上げなしで小数第2位に丸めた秒として表される。59.999秒は "60 seconds"、119.999秒は "1 minute and 60 seconds" と表示される。単位が単数形になるのは、その数がちょうど1のときだけなので、999ミリ秒は "1 seconds" と表示される。ゼロは "0 seconds"、無限の値は "forever" と表示される。

**算術。** 加算と減算は2つのタイムスパン間で機能する。減算はゼロで飽和し、どちらかのオペランドが無限なら、結果は両演算とも無限になる(永遠から永遠を引いても無限)。乗算は数をどちら側のオペランドにも取れる(負または NaN の因数なら値なし、ゼロの因数なら永遠でもゼロ、オーバーフローなら永遠となる)。

数による除算はミリ秒単位でゼロ方向へ切り捨てる(ゼロで割ると、被除数がゼロの場合を除き永遠となる)。一方、タイムスパン同士の除算はその数値比を返し、数やテキストとのその他の組み合わせはいずれも値なしとなる。オペランドが欠けている場合はもう一方の側のゼロとみなされ(乗算では数のゼロ)、両方のオペランドが欠けている場合は値なしとなる。

比較はミリ秒で順序づけられ(5秒は100ティックと等しい)、永遠はどの有限値よりも大きく、永遠自身とは等しい。数やテキストに対しては、等値も順序も偽になる。なお、エンジンの数の表示もついでにオリジナルへ合わせた。小数を含む数は小数第2位に丸めて表示される(5 / 3 は "1.67" と表示される)。

タイムスパンはローカル変数・グローバル変数・リスト要素に格納でき、エンジンの変数ストアに永続化され、関数のパラメータと戻り値の型として `timespan` / `timespans` を指定できる(複数形は値を収集し、デフォルト値も指定可能)。

**値型によって可能になった機能。** `waitFor(value)` はオリジナルの `wait <timespan>` をエミットし、変数または算術の結果を受け付ける(リテラルの wait は変更されない)。タイトルとサブタイトルのタイミングには式(リテラル、変数、算術のいずれか)を指定でき、未指定の部分と、式が値を持たない部分は、オリジナルのデフォルト 10 / 70 / 20 ティックへフォールバックする。

fishing 系の式 `fishingWaitTime("min" | "max")`、`fishingBiteTime()`、`fishingApproachAngle("min" | "max")` は、fishing イベント内で現在のフックの値を読み取る(キャスト時には 5秒、30秒、0秒、そして0度と360度)。対応するセッターがこれを再調整する。fishing イベントの外では、読み取りは値なしとなり、書き込みは何もしない。変数に対する add / remove ステートメントはタイムスパンを受け付け(remove はゼロで飽和)、`remove(variable, value)` は変数全般に対して新たに追加された。

**検証済み、ただし不採用。** ワールド時間は、オリジナルではタイムスパンと組み合わせられない。ワールド時間へのタイムスパン設定はチェンジャーエラー、`time in world + 2 hours` は値なしとなるため、フェーズ18の除外はそのまま維持される。周期を変数で指定した periodical(`every {_t}:`)はパースされるが、発火は一度も観測されていない。そのため、周期イベントはリテラル限定のままである。

"minecraft" 単位ファミリー(1 minecraft day は 20分と測られる)は別個のリテラル文法であり、後回しにしている。複合リテラル(`2 hours, 30 minutes`)はオリジナルに存在する(関数呼び出しの中では、隣接するリテラル引数同士が1つに結合されることさえある)。ただし API では、代わりに `plus()` で合成する。

ロードチェックで、3つの文法上のエッジケースが見つかった。裸のタイムスパンリテラルは文字列補間として使えない。リテラル数は `%{...}%` のリストインデックスとして使えない。静的に型付けされたタイムスパンと数の比較条件はロード時エラーとなる(変数を介する場合は、意味論が要求する通り false と評価される)。

## 日付と現在時刻

**日付**はミリ秒精度の時刻であり、クールダウンや締め切りの背後にある値である(フィードバック C3)。`now()` は式が評価される瞬間、`unixTimestamp(date)` は日付を UNIX エポックからの秒数として読み取り、`dateFromUnix(seconds)` はエポック秒から日付を再構築し、`differenceBetween(a, b)` は2つの値の間隔である。日付はコア言語であり、ビルダーはオリジナルの式をエミットし、エンジンは同じ IR を評価する。このセクションの内容はすべて、推測ではなく実物の Skript 2.17.1(2026年11月)に対して検証済みであり、いくつかの隅は一見自明な推測とは異なる。

**変換。** UNIX タイムスタンプは小数を持つ。ミリ秒が小数部分に乗るため、`unixTimestamp(now())` は `1794541239.13` のような数となり、このペアはミリ秒精度で往復する。逆方向の形式は `unix date of <number>` であり、`date from unix timestamp ...` という形式は存在しない(パースエラー)。型が違うオペランドは形式によって分かれる。変数を介する場合は値なしだが、型の違うリテラル(`unix timestamp of 5`、`unix date of "abc"`)はロード時エラーとなる。オリジナルがこれらの式の引数に型を付けているためである。

**差分。** `differenceBetween` はオリジナルの `difference between ... and ...` であり、常に絶対値である。2つの日付からは間隔がタイムスパンとして得られ(どちらの向きでも同じ値、自分自身との差は 0 seconds)、2つのタイムスパンからはタイムスパンが、2つの数からは数が得られる(10 と 3 なら 7)。混在したペア(日付とタイムスパンなど)と、欠けたオペランドは値なしである。

**シフト。** 日付にタイムスパンを足す・引く(`plus` / `minus` ビルダー)ことは、その時間分だけずれた日付であり、これが締め切りの書き方である。プレイヤーごとに `plus(now(), timespan(5, "minutes"))` を保存し、後で `now()` と比較し、残り時間を `differenceBetween(deadline, now())` として読み取る。`time` サンプルの `/cdstart` と `/cdleft` コマンドがまさにこの形であり、振る舞いテストは none → cooling → ready の流れを駆動する。このペアは非対称である。タイムスパン＋日付、日付－日付、日付＋数はいずれも値なしであり、2つの日付を引く唯一の方法は差分の式である。日付を保持する変数への add / remove ステートメントも同様にタイムスパンでシフトし、ただの数を add しても変数は変わらない(いずれも検証済み)。永遠が絡む隅は専用の検証なしにタイムスパンの規則へ従う。永遠のタイムスパンでのシフトは値なし、永遠を含む差分は永遠のままである。

**等値・順序・表示。** 日付はミリ秒数で比較される。約150ミリ秒離れた2つの `now()` は等しくなく、順序条件は期待通りに日付を並べ替える。日付は他の型の何とも等しくならない。日付の表示はオリジナルの設定された日付書式に従う。デフォルト設定(`date format: default`)では JVM のデフォルト SHORT/SHORT 日時形式となり、en_US / JST ホストでは `11/13/26, 12:40 PM` のようになる。エンジンも同じ JVM デフォルト形式で表示し、Skript の設定ファイルは読まないため、Skript の日付書式をカスタマイズしたサーバーでは、2つのランタイムで同じ日付の表示が異なる。値と比較には影響しない。

**型と格納。** 日付は関数のパラメータと戻り値の型に `date` / `dates` として使え(複数形はタイムスパンと同様に収集する)、ローカル変数・グローバル変数・リスト要素に格納でき、エンジンの変数ストアに永続化される(エポックミリ秒の `__date` レコード)。1点の相違は隠さず記録する。オリジナルでは日付への `type of` は `<none>` となるが、エンジンは値型への一様な命名に従い `date` と名付ける。振る舞いバッテリはどちらのモードでも日付の `type of` の行を固定しない。

**不採用。** 日付の書式化はこのフィードバック項目の範囲外である。カスタム書式文字列や書式付き日付式のビルダーはなく、日付はデフォルト形式でのみ表示される。テキストから日付を読み戻すことも同様に未対応である。

## 文字列のエスケープ

リテラルテキストは Skript の規則に従います。`"` は `""` に、リテラルな `%` は `%%` に
二重化します。対象は `str()` の値、`fmt()` のリテラル部分、権限文字列で、
出力済みプレースホルダには適用しません。
